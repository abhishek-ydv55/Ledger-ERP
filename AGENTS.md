# Multi-Tenant ERP System Architecture & Guidelines

This repository follows a strict set of architectural principles and design patterns. All future AI assistant sessions and developers MUST strictly follow these decisions.

---

## 1. Package Structure & Modularization

The backend follows a **Package-by-Feature** architecture located under `com.company.erp.modules.<module>`.

Each feature module must contain the following subpackages:
- `entity`: JPA Entity definitions (extending `TenantScopedEntity` or `BaseEntity`).
- `repository`: Spring Data JPA Repositories.
- `dto`: Request/Response records/classes.
- `mapper`: MapStruct mapper interfaces for converting between entities and DTOs.
- `service`: Business logic interfaces and implementations.
- `controller`: Spring REST controllers returning `ResponseEntity<ApiResponse<T>>`.
- `event`: Module-specific domain events (published or listened to).

### Mandatory System Modules:
1. `auth`: Authentication, JWT generation, login, token refresh, password resets.
2. `users`: User profiles, roles, permissions, user-tenant assignments.
3. `parties`: Customers, vendors, suppliers, contacts.
4. `items`: Products, raw materials, services, SKU management, unit of measure.
5. `inventory`: Warehouses, stock levels, stock movements, adjustments.
6. `sales`: Quotations, sales orders, invoices, credit notes.
7. `purchases`: Purchase orders, bills, goods receipt notes.
8. `payments`: Customer collections, vendor payouts, receipts.
9. `expenses`: Expense claims, petty cash, category management.
10. `banking`: Bank accounts, bank transfers, reconciliation.
11. `accounting`: Chart of accounts, journal entries, ledger transactions, fiscal years.
12. `reports`: Financial statements, balance sheet, P&L, trial balance, sales summaries.
13. `audit`: System audit logs, activity tracking, compliance history.

## 2. Multi-Tenancy Architecture

Multi-tenancy is enforced at the database row-level using Hibernate Filters and JWT Context.

### Key Rules:
- All tenant-specific entities **MUST** extend `TenantScopedEntity` (`com.company.erp.common.domain.TenantScopedEntity`).
- `TenantScopedEntity` defines `@FilterDef(name = "tenantFilter", parameters = @ParamDef(name = "tenantId", type = java.util.UUID.class))` and `@Filter(name = "tenantFilter", condition = "organization_id = :tenantId")`.
- Tenant context is managed by `TenantContext` (backed by `ThreadLocal<UUID>`).
- Request handling uses a `TenantInterceptor` (`HandlerInterceptor`) that extracts the `organization_id` (or `tenant_id`) from authenticated JWT claims / headers, sets `TenantContext`, and enables the Hibernate filter on the current Hibernate `Session`.
- **NEVER** write manual tenant filtering (`WHERE organization_id = :orgId`) in standard Repository methods or JPQL queries. Rely strictly on the automated Hibernate filter.

## 3. Cross-Module Integration & Domain Events

Cross-module side effects **MUST** be completely decoupled via domain events.

### Key Rules:
- Direct service calls across modules for write operations or side-effects are **STRICTLY PROHIBITED**.
- Modules publish domain events using Spring's `ApplicationEventPublisher` (e.g., `publisher.publishEvent(new InvoiceIssuedEvent(...))`).
- Downstream modules listen to events using `@TransactionalEventListener(phase = TransactionPhase.BEFORE_COMMIT)` to process side-effects (e.g., creating journal entries in `accounting` or updating stock in `inventory`) within the same transaction.
- **Exception**: Read-only query lookups across modules via service/repository interfaces are permitted (e.g., `sales` module reading customer details from `parties` for validation).

---

## 4. Entity Identification & UUID Generation

- Database primary keys **MUST** be UUIDs generated by the application layer using Spring / JPA standard annotations:
  ```java
  @Id
  @GeneratedValue(strategy = GenerationType.UUID)
  private UUID id;
  ```
- Do **NOT** rely on database-side defaults like `gen_random_uuid()` or `uuid_generate_v4()`. The application owns identity generation.

---

## 5. Standardized API Response & Exception Handling

All REST controllers MUST return a uniform response envelope and delegate exception handling to the global controller advice.

### Response Envelope:
Every endpoint returns `ApiResponse<T>` (`com.company.erp.common.response.ApiResponse`):
```json
{
  "success": true,
  "message": "Operation completed successfully",
  "data": { ... },
  "timestamp": "2026-09-27T15:00:00Z",
  "errors": null
}
```

### Global Exception Handler:
All unhandled exceptions are caught by `GlobalExceptionHandler` (`@RestControllerAdvice`):
- `ResourceNotFoundException` -> `404 NOT FOUND`
- `BusinessRuleViolationException` -> `400 BAD REQUEST` / `422 UNPROCESSABLE ENTITY`
- `InsufficientStockException` -> `400 BAD REQUEST`
- `MethodArgumentNotValidException` (Validation failures) -> `400 BAD REQUEST` with field error details
- `AccessDeniedException` / Security Exceptions -> `403 FORBIDDEN` / `401 UNAUTHORIZED`

---

## 6. Testing Strategy

- **NO H2 DATABASE**: H2 is strictly forbidden in test dependencies and runtime configurations.
- All integration tests MUST run against real PostgreSQL instances provided by **Testcontainers** (`org.testcontainers.postgresql.PostgreSQLContainer`).
- Base integration test class: `BaseIntegrationTest` configured with Spring Boot's `@ServiceConnection` / `@DynamicPropertySource`.
